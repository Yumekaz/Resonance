# M1.3A reconciliation baseline

## Environment and workload

- Run date: 2026-09-23.
- Windows 10.0.26200 x64, 16 logical CPUs, 16,473,051,136 bytes RAM, Go 1.25.0.
- PostgreSQL 17.11 on loopback, `max_connections=20`, `shared_buffers=128MB`, `fsync=on`; Resonance pool maximum is four.
- Repository drive: fixed NTFS volume, 206,886,137,856 bytes total and about 43.0 GB free. The restricted PowerShell session denied WMI/CIM access, so the physical disk model is unavailable.
- Corpus: 1,000 generated PCM WAV locations, 100 generated WAV locations in an incomplete-traversal subtree, and 20 CC0 MP3 metadata fixtures; 1,120 files and 53,293,360 bytes at baseline. The report stores a SHA-256 corpus manifest.
- The M1.2-state catalog rows were seeded with the same Track/MediaObject/MediaLocation IDs and size observations expected after migration 0005. The measured first pass hashed all 1,120 files once; baseline repetitions reset mtime observations to represent migrated M1.2 rows.
- Repetitions: ten per changed workload and twenty unchanged warm rescans. p50 uses the middle value or the mean of the middle pair; p95 and p99 use nearest rank `ceil(p*N)`. With ten samples, p95 and p99 are both the maximum sample.
- The first pass follows corpus generation. The OS filesystem cache was not forcibly cleared, so a true cold-cache condition is unverified. Warm runs immediately follow a completed hash pass.

Durations are milliseconds. Each p50/p95/p99 group summarizes full scan time; per-run `publish_transaction_ms`, SQL statements, and DML rows affected are in the raw artifact.

Unchanged rescans hashed zero files and extracted zero metadata. They performed final metadata-only stat rechecks before accepting the traversal, without opening or hashing unchanged files. Hashed files also received a final confined path stat check after their handle-level stability checks. The one-percent mtime-only workload hashed ten files and extracted no metadata. The native rename workload preserved ten locations; disabling native identity added ten new locations and made ten old locations unavailable after the complete scan. The incomplete workload never reconciled absence, and each complete follow-up applied the ten actual removals.

The baseline measured 53,293,360 hashed bytes. The benchmark process peaked at 152,334,336 bytes working set and used 123.141 seconds of CPU over the 243.121-second suite. PostgreSQL database size went from 15,505,075 to 25,990,835 bytes; observed WAL generation was 100,927,464 bytes. Workload samples include per-scan SQL statement counts, DML rows affected, and final publication transaction duration.

## Preserved M0 Range path

The client made 100 sequential random 64 KiB Range requests in each run. The concurrent figures below use the 95 requests whose individual start/end timestamps intersect the baseline scan; the other five are excluded. The client completed its full-transfer warm-up before the scan began.

| Condition | p50 | p95 | p99 |
|---|---:|---:|---:|
| Idle, 100 requests | 7.640 | 16.241 | 21.444 |
| Overlapping reconciliation, 95 requests | 4.556 | 6.213 | 6.424 |

The Range request burst overlapped the baseline scan for 2,207 ms. Its maximum measured request was 6.424 ms. All responses were checked for status, `Content-Range`, `Content-Length`, and exact consumed bytes. The earlier unreviewed benchmark counted process lifetime as overlap without request timestamps, so its concurrent p99 of 23.726 ms did not establish a reconciliation tail measurement. Idle and concurrent runs were sequential and have uncontrolled OS scheduling/cache state; this run does not demonstrate a latency improvement.
