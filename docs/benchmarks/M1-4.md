# M1.4 measured catalog and playback evidence

Run date: 2026-09-23. Host: Windows 10.0.26200 x64, 16 logical CPUs, about 16.5 GB RAM, Go 1.25, PostgreSQL 17.11 on loopback with 128 MiB shared buffers and `fsync=on`; Resonance pool maximum four. This was a dedicated local test cluster. OS and PostgreSQL caches were not reset. These are baselines, not SLOs.

## Catalog reads and Track resolution

The server had two scanned Tracks (one 26,460,044-byte WAV and one tagged MP3). `go run ./cmd/m14measure -base http://127.0.0.1:8080 -track <scanned-track-id> -count 100 -out docs/benchmarks/M1-4-queries.json` made 100 sequential warm requests for each route and 100 direct PostgreSQL `PlaybackCandidates` resolutions. The read requests consumed the entire JSON body. Values are milliseconds, p50 as the mean middle pair and p95/p99 by nearest rank.

| Operation | p50 | p95 | p99 |
|---|---:|---:|---:|
| Tracks page | 7.409 | 10.048 | 11.520 |
| Artists page | 6.608 | 7.831 | 13.504 |
| Albums page | 7.828 | 13.446 | 13.929 |
| Track detail | 8.324 | 9.912 | 10.455 |
| Track candidate resolution, SQL only | 0.536 | 0.765 | 1.349 |

After importing the 302-file corpus into the same catalog, the same 100-request command measured 304 Tracks: Tracks page **13.095/15.127/16.467 ms**, Artists page **7.881/9.412/13.055 ms**, Albums page **6.104/7.508/8.522 ms**, Track detail **5.934/7.757/9.762 ms**, and Track candidate resolution **0.567/1.466/1.995 ms** (p50/p95/p99). The first 304-Track measurement attempt timed out once waiting for a Tracks-page response; an immediate complete rerun passed. The cause of that timeout was not isolated, so the successful distribution does not include it. The raw successful outputs record each request time, status and request ID without host paths: [two Track run](M1-4-queries.json) and [304 Track run](M1-4-queries-304.json). Neither catalog is a 10k Track workload.

## Indexed Range and browser playback

The same 26,460,044-byte scanned WAV was served through `/api/v1/tracks/{id}/stream`. `go run ./cmd/bench -url http://127.0.0.1:8080/api/v1/tracks/<id>/stream -count 100 -out docs/benchmarks/M1-4-range-idle.json` checked one full transfer, the first Range, and 100 seeded random 64 KiB Ranges for status, content range, content length, and consumed bytes. Full TTFB was 5.613 ms and first Range TTFB was 5.479 ms.

| Condition | Range total p50 | p95 | p99 | Range TTFB p50 | p95 | p99 |
|---|---:|---:|---:|---:|---:|---:|
| Idle, 100 requests | 5.341 | 6.833 | 7.548 | 5.269 | 6.673 | 7.548 |
| Concurrent scan, 73 actual overlapping requests | 7.250 | 8.252 | 8.993 | — | — | — |

For concurrency, a 302-file/795,948,098-byte import started at **2026-09-23 06:47:52.5596086 UTC** and finished at **06:47:54.6603325 UTC**. Exactly 73 of the 100 random Range request intervals intersected that scan interval. The first overlapping request started at 06:47:52.5532983 UTC and the last finished at 06:47:53.0807823 UTC. The scan reported 2,120.847 ms total, 852.140 ms final publication, and 525.162 ms grouping within publication. All 100 responses passed the benchmark protocol checks. [Idle Range raw](M1-4-range-idle.json), [concurrent Range raw](M1-4-range-concurrent.json), and [scan event timestamps](M1-4-scan-events.jsonl) preserve the evidence. Idle and concurrent runs were sequential with uncontrolled cache and scheduling, so the difference is not an isolated grouping effect.

Independent review recalculated the 73 overlapping request samples from their individual timestamps. The nearest-rank p95/p99 are 8.2516/8.9931 ms; the raw median is **7.2503 ms**, correcting the earlier 7.244 ms transcription. A separate 100-request idle run after the resolver's root and path rechecks measured 9.839/13.491/16.428 ms p50/p95/p99. Its [raw requests](M1-4-review-range-idle.json) were collected with `go run ./cmd/bench -url http://127.0.0.1:18080/api/v1/tracks/<scanned-track-id>/stream -count 100 -out data/m14-review-range.json` on the same Windows/PostgreSQL host, using a two-Track review catalog and uncontrolled caches. Different server state and cache conditions prevent a causal comparison with the original run.

In Chrome with 256 KiB/s throttling and 20 ms simulated latency, the real-library UI advanced playback after 515,306 of 26,460,044 bytes had transferred in the final browser run. Seeking issued a new `206` for `bytes=18513920-` with `Content-Range: bytes 18513920-26460043/26460044`; seek-to-`playing` was 194.8 ms in that single run. The automated browser test also traversed Artist → Album → Track. [Browser evidence](M1-4-browser.json) records the final passing sample. Browser playback progression is not proof that sound was audible from a physical phone; physical same-LAN phone demonstration verified on 2026-09-23.

## Added publication work

On the existing 302-file M1.2 corpus, the first authoritative import measured **818.912 ms** in grouping inside a **1,803.349 ms** final transaction. Ten subsequent unchanged scans skipped regrouping (`grouping_ms=0` in every raw record); their publication p50/p95/p99 was **220.525/413.358/413.358 ms**. The run command was `resonance library scan <enrolled-root-id>` once for import and ten times unchanged; [the repeatable harness](../../tools/m1-4-publication-benchmark.ps1) records the same fields for a fresh enrolled test root. [M1-4-publication.json](M1-4-publication.json) stores dataset bytes, exact per-run start/end timestamps, scan counts, transaction time, and grouping time. A later improvement restricts changed-scan membership writes to affected Tracks and their Album peers. In a 304-Track catalog, one source retag measured 13.985 ms grouping within 30.872 ms publication; restoring the original bytes measured 14.512 ms grouping within 27.026 ms publication. Those are two samples, not a tail distribution; [raw changed-scan evidence](M1-4-changed-publication.json) preserves timestamps and counts. The [M1.3A baseline](M1-3A.md) used 1,120 files and different workloads, so these numbers do not establish an apples-to-apples latency delta.

## Fault evidence and limits

A dedicated PostgreSQL test process was stopped and restarted. During the outage, `/health` and demo metadata remained 200, `/ready`, catalog reads, and new indexed streams returned 503 with `catalog_unavailable`; after WAL recovery, readiness, reads, and stream HEAD returned 200. [The status matrix](M1-4-database-fault.json) records the manual observation, whose individual request timestamps were not captured. Automated integration tests cover a failed grouping publication transaction, interrupted/retried backfill, unavailable and reappearing Tracks, alternate location fallback, changed/disappeared candidates, established-stream reconciliation, cancellation, and post-header truncation.

Physical same-LAN phone demonstration verified on 2026-09-23. The OS cache was not safely evicted, the largest catalog read benchmark used 304 Tracks, and no hard latency SLO is claimed.

Independent review attempted to reproduce the unexplained Tracks-page timeout against isolated synthetic 304-Track PostgreSQL catalogs using the benchmark client's 10-second request timeout. Three 100-request attempts all completed; their observed maxima were 27.035, 48.977, and 292.944 ms. A paginated pass also returned all 304 Track IDs without duplicates while one location's availability changed between pages; a Track cursor was rejected on the Artist route. The original failed attempt was not retained as request-level raw evidence or a server trace. The failing operation is documented as a Tracks-page response, but its cause remains unknown and its timeout is excluded from the successful percentile distribution.

The initial 302-Track grouping pass performs several SQL writes per Track and measured 818.912 ms inside publication. A changed scan still loads all rooted Track grouping inputs to build evidence and year maps before writing affected memberships; the single retag's 13.985 ms is therefore not constant-time evidence. Query costs and publication behavior at 10k Tracks remain unmeasured.
