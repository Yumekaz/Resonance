# M1.5 queue, playlist, favorite, history, and stream evidence

Run date: 2026-09-24. Host: Windows 10.0.26200 x64, 16 logical CPUs, about 16.5 GB RAM, Go 1.25, PostgreSQL 17.11 on loopback with 128 MiB shared buffers and `fsync=on`; Resonance pool maximum four. The database was a dedicated local test cluster. Caches were warm and not reset. All figures are local baselines, not SLOs. p50 averages the middle pair for even sample counts; p95/p99 use nearest rank.

Independent review recalculated the reported percentiles from both raw storage sample files and the concurrent/idle Range and catalog samples; values match the tables below. These measurements predate the corrected working-tree changes recorded in ADR-007 and are not a benchmark of the corrected tree.

## Transaction costs

`RESONANCE_TEST_DATABASE_URL=<dedicated database> RESONANCE_M15_BENCHMARK_OUTPUT=<fresh output> go test -p 1 -tags=integration -run TestM15BenchmarkEvidence -count=1 ./internal/storage` measured one rooted Track referenced by 1,000 queue occurrences and 500 playlist entries. Reads, adds, removes, favorites, and several history operations have 100 or 30 sequential samples as shown; reorder uses 30 samples. The [expanded raw file](M1-5-raw-expanded.json) preserves each start/end time and duration. The earlier [initial raw run](M1-5-raw.json) is retained as an intermediate measurement with fewer playlist operations.

Dense reorder and playlist removal pay for many row updates. The 1,000-item queue reorder p99 was 507.992 ms; this is a measured cost to monitor, not a reason to introduce another ordering system without a real workload requirement.

The raw benchmark measures end-to-end operation time, not lock-only time. `ReorderQueue` takes the active-queue row lock before reading and updating item positions and holds it through receipt insertion and commit, so that measured 507.992 ms p99 is an upper bound on the queue-writer lock interval for this sequential run. Concurrent queue writes serialize during the reorder; queue reads use MVCC and indexed media streams do not take this queue lock. This is no observed correctness failure, and the measurement does not establish a latency SLO.

## Catalog and Range overlap with queue writes

The existing 26,460,044-byte indexed WAV was requested through `/api/v1/tracks/{id}/stream`. `cmd/bench` made 100 seeded random 64 KiB Ranges, checking status, `Content-Range`, `Content-Length`, and bytes consumed. `cmd/m15burst` repeatedly reordered 100 durable queue occurrences in the **same catalog schema** while preserving request and mutation start/end timestamps. All **100** Range request intervals overlapped the write interval **2026-09-24 05:37:47.2876734–05:37:52.3078143 UTC**; the last overlapping Range finished at **05:37:48.4318036 UTC**. [Concurrent Range raw](M1-5-range-concurrent.json), [write raw](M1-5-write-overlap.json), and [idle Range raw](M1-5-range-idle.json) preserve the samples.

| Range condition | p50 ms | p95 ms | p99 ms |
|---|---:|---:|---:|
| Concurrent queue reorder, 100 requests | 11.193 | 13.508 | 14.864 |
| Later idle run, 100 requests | 10.651 | 12.573 | 14.288 |

`cmd/m15catalogbench` also made 100 validated Tracks-page reads during a separate 100-reorder burst. All **100** page intervals overlapped the write interval **2026-09-24 05:41:27.2844609–05:41:30.9802500 UTC**; the last page finished at **05:41:28.9039493 UTC**. Concurrent catalog p50/p95/p99 was **16.134/18.734/19.467 ms**; a later idle run was **20.300/24.161/28.466 ms**. The [catalog raw](M1-5-catalog-concurrent.json), [write raw](M1-5-write-catalog-overlap.json), and [idle catalog raw](M1-5-catalog-idle.json) show each interval. An initial overlap attempt failed because the harness reused a previous run's deterministic idempotency keys; the harness now generates a fresh key prefix for each run. Idle and concurrent runs were sequential with uncontrolled cache and scheduling, so these differences do not establish a causal latency change.

## PostgreSQL outage and recovery

After response headers for an indexed full GET were received, the dedicated PostgreSQL test cluster was stopped. The already-open stream delivered all **26,460,044 of 26,460,044 bytes**. During the outage `/health` and demo metadata returned 200; `/ready`, queue, playlists, favorites, and history returned typed 503. After restart they returned 200. [M1-5-fault.json](M1-5-fault.json) records timestamps, statuses, and bytes. Automated HTTP integration tests also assert 503 for mutations with a closed catalog pool.

## Limits

These measurements use one distinct Track replicated as queue and playlist occurrences, not a representative household catalog. The overlap tests use a 100-item reorder; the isolated worst-case reorder uses 1,000 queue items and 500 playlist entries. No OS cache eviction was attempted. Browser tests prove event and protocol behavior, not that sound was audible. A physical same-LAN phone control run was not performed for M1.5.
